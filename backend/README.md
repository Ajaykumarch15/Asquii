# Asquii API backend

Sprint 1 provides a FastAPI foundation. It does not implement authentication, business APIs, product tables, or RLS policies. No frontend source files are part of this setup.

## Prerequisites

- Python 3.11 or 3.12
- PostgreSQL 14+ for a local or nonproduction Supabase database
- The pinned Python dependencies in `requirements.txt`

Create and activate a virtual environment from this directory, then install dependencies:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Copy `.env.example` to `.env` and set appropriate local/nonproduction values. Never commit `.env` or place credentials in frontend configuration. Development can start without a database URL; `/ready` then returns 503. Staging and production require database, Supabase URL/key, and an explicit CORS allowlist.

## Run locally

```powershell
uvicorn app.main:app --reload
```

The default API docs are at `http://127.0.0.1:8000/docs`. `GET /health` is a process liveness check and never accesses PostgreSQL. `GET /ready` runs a bounded `SELECT 1` and returns only a safe status. `GET /api/v1/` returns basic API metadata. Every response includes an `X-Request-ID`; a safe incoming ID is propagated, otherwise one is generated.

## Database and Supabase

The engine uses SQLAlchemy 2.x with synchronous Psycopg 3, `pool_pre_ping`, a small pool (3 connections plus at most 2 overflow), and a 5-second connection/pool wait bound. Psycopg prepared statement caching is disabled for compatibility with transaction poolers. For app requests, use the Supabase transaction pooler URL (commonly port 6543). Keep migration operations on the direct/session connection (commonly port 5432) and run them as a controlled operator/release step.

The project has no supplied staging credentials, network access details, or approved Supabase role configuration. Live connectivity and migration execution have therefore not been verified. Direct SQL access does not establish end-user RLS identity. Sprint 1 has no JWT verification or authenticated user requests; never use a service-role credential for request handling. Before tenant queries are implemented, prove transaction-local identity propagation, grants, `auth.uid()`, pool reset behavior, and the app role's `BYPASSRLS` attribute through the actual staging pooler. If those checks cannot be proven, use the Supabase Data API with the end-user JWT for RLS-scoped work.

## Alembic

The initial revision is intentionally empty. It creates no product tables. Set a nonproduction `DATABASE_URL` before running commands from this directory:

```powershell
alembic upgrade head
alembic downgrade base
alembic revision --autogenerate -m "describe schema change"
```

Review autogenerated migrations before applying them. Never run migration verification against production. The migration connection should be direct/session mode, not the transaction pooler.

## Tests and code quality

Tests use isolated settings and mocked database readiness, so they do not need Supabase credentials:

```powershell
python -m pytest
ruff check app tests
ruff format --check app tests
```

Direct dependency versions are pinned in `requirements.txt`; install it in a clean virtual environment for consistent direct package versions. No lockfile has been generated in this environment.

## Security and operational notes

- CORS has no wildcard origin; configure explicit browser origins.
- Production/staging configuration fails when required settings are missing.
- Error responses omit exception details and database information.
- Logs are structured JSON and do not log configuration values or request bodies.
- Configure request body size limits at the ingress/server before accepting write APIs; no write endpoints exist in this sprint.
- No trusted proxy headers are enabled. Add them only for a known, controlled proxy topology.
- OpenAPI is enabled by FastAPI defaults; restrict it at deployment if public exposure is not intended.
- No app startup migration execution, authentication, authorization, or RLS policy is included.

## Troubleshooting

- `ModuleNotFoundError`: activate the virtual environment and install `requirements.txt`.
- `/ready` returns 503: check `DATABASE_URL`, network access, database availability, and connection mode; the response intentionally hides driver details.
- Alembic cannot connect: use the staging direct/session URL and check allowlisting; never paste credentials into logs or source.
- Production settings validation fails: set `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `CORS_ORIGINS` in the deployment secret/configuration system.
