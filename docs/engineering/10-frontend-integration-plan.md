# 10 — Frontend integration plan

Keep the existing React + TypeScript + Vite implementation and component/page organization. This is an incremental data/auth integration plan, not a redesign. No router, query cache, Supabase SDK, or schema validator is currently declared.

## Identity and API boundary

React should use the Supabase Auth SDK for session lifecycle and send the access JWT to FastAPI. Replace `personaId` as identity only when auth UI is approved; the current picker is prototype-only. Suggested organization: `src/lib/auth/` for Supabase client/session, `src/lib/api/client.ts` for base URL/token/error handling, and domain `api.ts` modules under existing workspace/project module folders. Keep screen components working through props/callbacks initially.

FastAPI validates the token and derives user identity/roles from PostgreSQL. Client must never submit authoritative role or user identity. API list access includes every active project in the workspace; read-only state for non-project members should be reflected in existing action affordances when integrated. Owner/Admin and Project Manager rules are documented in [08](08-authentication-authorization.md).

## Data migration by page

The Sprint 4 backend contract now includes workspace create/list/get/update/archive, member list/detail/role/removal, ownership transfer, and invitation create/list/revoke/accept endpoints. Workspace creation takes `{name}` and returns its generated slug and Owner role. Member role changes use `/members/{uid}/role`; transfer uses `/transfer-ownership`; archival uses `/archive`; invitation acceptance posts `{token}` to `/api/v1/invitations/accept`. The invitation creation response contains a one-time plaintext token for manual sharing; invitation list responses do not contain token material. Member removal returns conflict while project roster entries still exist, so the UI should explain that project assignments need resolution first.

Sprint 5 adds workspace-scoped project and milestone endpoints under `/api/v1/workspaces/{wid}/projects`. Project lists support `status`, `q`, `limit`, and `offset`; details include the caller's project role and roster counts. Project Manager transfer uses `/projects/{pid}/transfer-manager`; milestone operations use `/projects/{pid}/milestones`. Project archival is read-only afterward. Removing a project member can return 409 when that roster row is still referenced by task assignments, comments, attendees, or resources; the UI should preserve current state and explain that dependent project records need reassignment first.

Sprint 6 adds task routes at `/api/v1/workspaces/{wid}/projects/{pid}/tasks`, with bounded list filters (`q`, status, priority, assignee, due-date range, sort, limit, offset), task create/detail/update/delete, and explicit assignee updates. Subtasks are nested under a task and expose title, completion, and position. Comments are nested under a task, paginated, editable by their author, and deletable by their author, a Project Manager, or a workspace Owner/Admin. Comment deletion hides the body while retaining the row. Task deletion returns 409 while any comment record exists; subtasks cascade. Assignee choices must be current project members. The current schema has no task creator column, so the API can return creator information only when activity history records it. Workspace Owner/Admin users outside the project roster cannot create comments under the existing comment-author FK; surface the 409 and ask a project member to post. The backend does not infer project progress from subtask completion.

Sprint 7 adds meetings and resources under the same workspace/project scope. Meeting lists support title query, timezone-aware start range, pagination and allowlisted sorting. Meeting fields are `title`, `description`, `starts_at`, `duration_minutes`, `meeting_type`, and `agenda`; the end time is derived. Attendees are active project members. Owner/Admin and Project Manager administer meetings/attendees; attendees may remove themselves. Since the schema has no meeting status or organizer column, DELETE removes the meeting and its attendee rows, while organizer display is available only from the creation activity event. Resource lists support query, type, category, owner, starred filters, pagination and sorting. The authenticated project member owns a newly created resource; updates/deletes are allowed to that owner, with Owner/Admin and Project Manager overrides. DELETE soft-deletes the resource. Star state is per-user and idempotent; it does not generate a shared activity event. Resource stars cannot be changed for archived or deleted resources. Workspace admins outside the project roster may encounter 409 when creating a resource because the schema requires its owner to be a project member.

Sprint 8 exposes workspace and project activity pages as `{items, total, limit, offset}`. Use `GET /api/v1/workspaces/{wid}/activities` for the combined workspace/project timeline and `GET /api/v1/workspaces/{wid}/projects/{pid}/activities` for one project's events. Filters include actor, action, resource type (the stored `entity_type`), and inclusive `starts_after`/`starts_before`; the workspace feed also accepts `project_id`. Sorting is allowlisted and defaults to newest first. Detail routes scope IDs to the parent workspace or project. Actor display name may be null for missing profiles; metadata is JSON but known private content keys are removed. Do not depend on RLS identity until ADR-008 staging verification is complete. ADR-010's DB writer boundary also remains unverified, so the feed is not evidence that activity inserts are database-restricted to trusted code.

Workspace overview/projects load all active workspace projects and aggregates. People/settings use member/invitation/settings APIs. Project screens load project details and child rows; non-project workspace members can view all active project content but cannot write. Project settings/membership controls require Owner/Admin or Project Manager. Task assignments, meeting attendees and resource owners are restricted to project members. Resource star state is per-user.

Replace `useAppData` aggregate persistence a domain at a time, preserving page contracts. Decide whether to import, export, or discard `asquii.prototype.v8` data before rollout; do not silently promote seed records into shared production data. Existing local theme/recent navigation may remain client preferences. Notification read/preferences become server-backed only if conditional notification features are approved.

## Loading, errors, forms, lists

Wire current `LoadingState`, `ErrorState`, `EmptyState`, and `StateMessage` to real requests. Show loading on initial fetch, retry network failures, preserve form drafts on recoverable errors, disable duplicate submission, and map Pydantic field errors to inputs. 401 uses SDK refresh/session handling; 403 gives access-denied; concealed cross-tenant misses consistently return 404; 409 identifies duplicates/concurrency; 422 maps validation; 429 gives retry guidance. Never fall back to fixtures silently in production.

Use bounded server pagination for larger collections. Current local sorting/filtering may stay for already loaded small sets; otherwise send allowlisted filters and sort. CSV export can remain client-side for fetched data; bulk import needs a separately scoped endpoint. Board ordering may update optimistically with rollback on failure; invitation, role, archive, and purge operations should wait for server confirmation.

## RLS interaction

Frontend JWT is forwarded to FastAPI, where validated identity is propagated transaction-locally to PostgreSQL for RLS if the direct SQLAlchemy strategy passes staging verification. Frontend never configures DB claims. If direct connection context is unreliable, FastAPI may use Supabase Data API with the end-user JWT for RLS-scoped calls. See [08](08-authentication-authorization.md).
